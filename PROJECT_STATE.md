# Sprouted Group — Project State

Read [CLAUDE.md](CLAUDE.md) first — it contains the non-negotiable accounting rules. This file describes where the project stands right now, for any developer or AI picking it up.

## Stack

- Next.js 16.3.5 (App Router) + React 19 + TypeScript
- Tailwind CSS 3.4 (Xero-inspired warm neutral design system in `src/app/globals.css` and `src/components/ui/`)
- Prisma 6 + **Postgres** (`prisma/schema.prisma`, migrations in `prisma/migrations/`). Hosted on Supabase; a local Postgres works identically. See `.env.example` for which connection string is which — the transaction pooler for the app, the session pooler for migrations.
- Vitest (`npm test`) — no test touches a database.
- ESLint flat config (`eslint.config.mjs`); `npm run lint`.

## What is built

All current UI lives in `src/components/app/app-shell.tsx` (single shell, sidebar navigation). Each module:

- **Dashboard** — cash position, money owed to us, money we owe, intercompany balance; shared contacts with per-entity balances; entity switcher; add-entity form
- **Sales / Purchases** — Xero-style invoice and bill editor, **persisted in Postgres**. Line items with description, quantity, unit price (entered in cedis, stored in pesewas), account (from the entity's own chart), VAT treatment (standard / zero-rated / exempt). Ghana VAT split: 15% VAT + 2.5% NHIL + 2.5% GETFund on the same base, shown separately. Bills withhold WHT (5%/10%) based on the supplier's status and show net payable. Drafts autosave to the server (debounced). **Posting** allocates the number server-side (`INV-0001`), writes a balanced `JournalEntry` dated the document's date inside one transaction with its audit event, and is guarded against double-posting. **Voiding** writes a reversing entry dated today (refused if today's period is filed); the original is untouched. **Recording a payment** (see Multi-currency) posts the bank, relieves the receivable or payable, and books any realised FX difference. The journal panel shows the persisted entry once posted, a preview while a draft. Recent documents are listed above the editor. Server functions live in `src/app/actions/documents.ts`; the pure logic in `src/lib/documents.ts`. E-VAT placeholder fields exist on invoices — no GRA integration yet.
- **Bank** — CSV import with first-import column mapping saved per bank; two-column reconciliation (bank lines left, suggested matches right) with confidence scores from amount/date/contact; keyboard operated (arrows + Enter); in-row account coding; bulk match for repeated identical transactions; undo match; unreconciled counter.
- **Intercompany** — one entry posts both sides: sales invoice on the source entity and mirrored purchase bill on the target, linked by a shared reference. Group balance matrix across all entities (scales past three) with mismatch highlighting. Related-party report with both journal entries side by side.
- **Tax** — per-entity VAT return per period (output VAT, input VAT, NHIL, GETFund, net position), every figure clickable to drill into transactions. Filing a period locks it (`TaxPeriodFiling`, persisted): documents dated in a filed period cannot be posted, and a void's reversal must land in an open period. Periods that only existed in localStorage are imported once on first load. WHT report per supplier with TIN and CSV export for GRA. The return itself still reads demo `taxTransactions`, not posted documents.
- **Reports** — trial balance, profit & loss, balance sheet, cash flow, aged receivables, aged payables. All take a date range, are entity-scoped, include a prior-period comparison column, and every figure drills into the underlying ledger lines. Fund report (restricted/unrestricted, closing balance per fund) for Sprouted Roots only. **Project tracking** (Reports → Projects): each Sprouted Roots project (funder, restricted/unrestricted fund, budget) shows opening balance, funds received, expenses and closing balance per period with a budget-usage bar, all clickable to transactions; CSV export. Group view with all entities side by side plus a total column, clearly labelled as a management summary (not statutory consolidation, no eliminations). Every report exports to Excel (CSV) and PDF (browser print with print stylesheet).
- **Authentication and access** — **Better Auth** (`src/lib/auth.ts`), email + password, invite-only: there is no sign-up endpoint. An Owner invites by email from **/admin/users**, choosing a role and the entities the person may see; the invitee sets their own password from an emailed link that expires after 48 hours (the library's reset-password token — the credential is created on first use). Passwords: 12 characters minimum, checked against Have I Been Pwned (k-anonymity, via the library's plugin), no expiry or complexity rules. Sign-in is rate-limited per IP (5/min) by the library, and an account locks after **ten** failed attempts across any IPs until an Owner unlocks it (`/admin/users`). Roles: **Owner** (everything, all entities, manages users), **Accountant** (draft, post, reconcile, void, file periods), **Data entry** (drafts and bills only), **Viewer** (reports only). **Entity access is separate from role** (`UserEntityAccess`); Owners hold every entity implicitly. **TOTP is mandatory for Owners and Accountants** — the roles that can post — enforced at first sign-in: the home page redirects to `/two-factor/setup` and every Server Function refuses until a code has been verified. Ten backup codes are issued once. **Users are never deleted**: deactivation sets `deactivatedAt`, bans, and revokes every session; the id stays valid for every journal, document, filing and audit event that references it. **/admin/sessions** lists every live session (person, device, IP, last active) and an Owner can force sign-out; sessions last 12 hours and there is no cookie cache, so revocation takes effect on the next request. The first Owner is created from the command line (`npm run auth:create-owner`). **Email sender per entity:** `Entity.emailFrom` (Settings → Email, Owner only, audited) is the address a person's invitation and password reset come from — the first entity they have access to by code; Owners and unset entities use the group `EMAIL_FROM`. A sender must be on the same domain as `EMAIL_FROM`, the one verified with the provider, or it is refused at save time rather than at send time. Only these two emails exist; the app does not yet email invoices or statements to customers.
- **Multi-currency** — GHS, USD and EUR. Each entity has a **functional currency** (`Entity.functionalCurrency`, changeable only while its ledger is empty). **Every journal line stores four things permanently**: `txnCurrency`, `txnAmountMinor`, `rate` (Decimal 20,10) and `amountMinor` — the functional amount, fixed at posting and never recomputed. Rates are "functional units per 1 unit of transaction currency", applied with integer arithmetic scaled by 1e10; rounding differences from converting each line separately land on the control account so both currencies balance exactly. **Rate table** (`ExchangeRate`, per entity, per pair, per date, entered in Settings): a document defaults to its date's rate, else the most recent prior one with a visible warning, and can be overridden; changing the date re-defaults it. **Bank accounts** (`BankAccount`) are one currency each with their own GL account under 1001; balances are never stored converted. **Payments** (`Payment`, replacing "mark paid"): amount, bank, date and settlement rate; the journal debits/credits the bank at the settlement rate, relieves the receivable/payable at the document's historic rate, and posts the difference to **7010 Realised FX** — the calculation is shown on the payment panel before posting. Partial payments are allowed; the final one relieves the exact remaining book value. **Revaluation** (`Revaluation`, Settings → Period end): revalues foreign monetary balances (bank accounts, 1010/1015/1020/1025–1027, 2001/2015–2017 — never inventory or fixed assets) at closing rates, dated the last day of the period, to **7020 Unrealised FX**; the adjustment line carries a zero foreign amount so the foreign balance is untouched; one per period; reversible on the first day of the next. **UI**: `Money` always shows a symbol (GH₵, $, €) and defaults to the entity's functional currency via context; invoices show the foreign amount prominently with the functional equivalent beneath; the journal panel shows transaction amount, rate and functional in/out. **Reports** run in the functional currency with a "Show in USD/EUR" translation at a chosen closing rate, banner-labelled as a translation and echoed in the CSV header. **Intercompany matrix**: pairs with the same functional currency must net to zero (mismatch flag); pairs with different currencies show the mirror translated at today's rate and the FX difference explicitly. Pure logic in `src/lib/fx.ts`; server functions in `src/app/actions/fx.ts`.
- **VAT: dormant but ready** — none of the three entities is VAT registered, and the seed says so. Registration is **per entity, off by default** (`Entity.vatRegistered`, `vatRegisteredFrom`), switched on by an Owner under Settings with the date it takes effect, audited. `vatAppliesOn(entity, date)` in `ghana-tax.ts` is the only rule: registered **and** the document is dated on or after the registration date — never retrospective. **Off:** no VAT lines on invoices or bills, no levies calculated, totals are gross, the per-line VAT column reads "Supply type" (taxable / zero-rated / exempt — a classification that feeds the threshold tracker, charged nothing), and the Tax screen is hidden from the nav. VAT a supplier charged is **not recoverable**: the gross goes to the expense or inventory account, nothing to 1101–1103 — the branch in `buildJournalEntries` says so in a block comment because it reverses the moment registration takes effect. **On:** 15% + 2.5% + 2.5% on the same base for that entity only; the other entities are unaffected. The answer is **fixed on the document at posting** (`Document.vatApplied`) so a later switch, on or off, never changes how a posted document reads or what a payment relieves. **Imports:** bills carry `importVatMinor` (VAT paid at the port at 20%); unregistered it is cost, pro rata across the bill's cost accounts; registered it is input tax, split 15/2.5/2.5 into 1101/1102/1103. **Exports:** invoices carry `saleType` (domestic / export); zero-rated once registered, nothing changes while not. **Threshold tracker** on the dashboard: rolling twelve-month taxable turnover (posted invoices, standard + zero-rated lines, functional currency) as a percentage of GHS 750,000, amber at 75%, red at 90% and past 100%. Settings carries the note that suppliers of services must register regardless of turnover. Server function: `src/app/actions/vat.ts` (Owner, `entity:configure`). The seed never writes `vatRegistered` on update, so a re-seed cannot undo a registration.
- **Inventory (commodity trading)** — Sprouted Crafts trades raw cashew nuts and Oikazi trades cocoa beans; neither processes anything, and Sprouted Roots is an impact programme that holds no stock (`holdsStock`; Roots has no Inventory or Buying screen and refuses every stock function). A **commodity** (`Commodity`) has a kind (cashew / cocoa / other, which decides the quality fields), a configurable **kg per bag**, and a **shrinkage tolerance %**. Its **grades** are `Item` rows (`commodityId`, `grade`), counted in bags through the commodity's factor; **every quantity is stored as integer grams** — the money rule applied to weight. **Costing is weighted average per commodity × grade × location, never per lot**: each `StockBalance` holds quantity and value and the average is value ÷ quantity, so transfers, adjustments, counts and shrinkage all value at the location's own average and the ledger can never drift. **Lots** (`Lot`) exist for traceability and quality only — one per bill line or field purchase that receives a grade — carrying date, supplier or farmer, community and district, and the commodity's quality data (cashew: KOR, moisture %, nut count; cocoa: grade, moisture %, bean count); they track weight in and shrinkage, never cost. **Landed cost**: a bill line can be capitalised as transport, bags, loading, fumigation, levy or agent commission and is spread per kilogram over the lots it names (`allocateByWeight`, exact), raising their grades' value at their locations with quantity unchanged; voiding the bill takes it out again. **Weight loss**: a weigh-out on a lot records weight out; loss within the commodity's tolerance (cumulative over the lot's life) reduces quantity only — the remaining stock carries the cost — and loss beyond it posts to `5045 Stock Loss` at the location's average. Locations, counts and NRV are unchanged below. **Receipts come from bills**: a bill line to an inventory account names an item and a location; posting the bill creates the receipt at that line's share of what the journal debited to the account (`allocateReceiptValues`, exact to the pesewa, import VAT included while unregistered), so the bill's journal *is* the receipt's posting and nothing posts twice; a foreign bill is fixed at the bill's rate like every other foreign transaction. Voiding a bill reverses its receipts at the received value, and is refused if the stock has since moved. **Transfers** move quantity and value at average cost and post a `STOCK` journal only when the two locations carry the item in different accounts. **Adjustments** need a reason (count difference, moisture loss, damage, spoilage) and post the value difference to `5030 Inventory Adjustments`; nothing is applied silently. **Stock counts**: a data-entry user can save a count draft against a location; the screen shows expected vs counted, previews every difference and its value, and an Accountant posts it only after ticking a confirmation — one adjustment per difference, one journal. **NRV**: a selling price per kg per item per period; the report flags every item whose average cost exceeds it with the write-down needed, and a write-down posts to `5035 Inventory Write-downs (NRV)` leaving quantity unchanged. **Live stock value** per entity is shown against the ledger balance of every account tagged `inventory`, per account, from the real journal lines; any difference is a red warning naming the account. Permissions: `inventory:manage` (commodities, grades, locations, agents, the float age limit), `stock:enter` (count drafts, NRV prices, syncing field purchases — includes Data entry, which is what buying agents are), `stock:post` (transfers, adjustments, posting counts, write-downs, weigh-outs, floats, posting purchases). Pure logic in `src/lib/inventory.ts` and `src/lib/trading.ts`, server functions in `src/app/actions/inventory.ts` and `src/app/actions/trading.ts`, the screens in `inventory-panel.tsx` and `buying-panel.tsx`.
- **Buying agents and floats** — an agent (`BuyingAgent`, per entity, with a default receiving location) receives a **float** (`FloatAdvance`): money out of a bank account into `1060 Agent Float Advances`, a receivable. The agent records purchases on a phone at **/field**; each synced purchase (`AgentPurchase`: farmer, community, district, grade, bags and weight, price paid, cash or mobile money, quality) is **pending** until an Accountant posts it, which receives the stock at the agent's location against the float (`1030 Dr / 1060 Cr`) and creates the lot. Cash the agent hands back is a **float return** (bank Dr / 1060 Cr). A float **reconciles** only when advanced = purchases posted + cash returned, exactly, with nothing pending on it. The dashboard shows **outstanding float per agent**, red when the oldest open float is older than the entity's age limit (Settings under Buying, default 14 days). **/field** is a separate mobile-first page: one column, 52-px targets, numeric keyboards, bags converted through the commodity; a service worker (`public/field-sw.js`) keeps the page and its scripts so it opens with no signal, reference data is kept in localStorage from the last online load, and each saved purchase is queued locally with a client-generated reference and synced when the connection returns (`syncAgentPurchases` reports accepted / duplicate / rejected per record, so a resend can never double-record). The sync needs the agent's session cookie, which lasts 12 hours; a queue older than that syncs after the agent signs in again.
- **Sales contracts** (trading entities) — a contract (`SalesContract`, numbered `SC-0001`…) records buyer, commodity grade, quantity, price per kg / bag / tonne, currency (with the **contract rate** it was priced at, for foreign contracts), delivery terms, delivery period, whether revenue is recognised **on delivery or on the buyer's acceptance**, and domestic/export. Terms are fixed once a delivery exists. **Deliveries** draw stock from a chosen location at that location's weighted average (`issue`), value the revenue at the contract price in the contract currency and fix it in functional at the delivery-date rate (the receivable and revenue journal lines carry the foreign currency, so period-end revaluation sees them), and post one `CONTRACT` journal: Dr Receivables / Cr Domestic or Export Sales, Dr COGS / Cr Inventory. On-acceptance terms move the cost to a system location *Delivered, awaiting acceptance* carried in `1050 Goods in Transit` (so stock still reconciles to the ledger) and post revenue and COGS when the delivery is accepted. A contract closes itself when fully delivered; over-delivery is refused. **Selling costs** are bill lines attributed to a contract (transport to buyer or port, port handling, export permit, levy, other): they post to whatever expense account the line chose and count against the contract's margin; a void drops the attribution. **Margin per contract**: revenue, cost of stock delivered, selling costs, gross margin and margin per kg — and for a foreign contract the recognised revenue restated at the contract rate and at today's rate, plus the **FX exposure** on the undelivered balance at both rates. **Position report**: contracted-but-undelivered (open contracts) against stock on hand per grade, flagged oversold (red) or unsold (amber). **LBC mode** (per entity, Owner): when on, **seed funds** received are `2050 COCOBOD Seed Fund Payable` — a liability, never income — repaid or offset against the COCOBOD receivable; the field form defaults the price to the **gazetted producer price**; a **CMC contract** delivers to a take-over centre and is owed by `1065 COCOBOD Receivable`; **buyer's margin** (`4020`) and **haulage allowance** (`4025`) post as separate income at the per-kg rates set; and the **gross / net** setting decides the journal: gross posts producer value to Sales and cost to COGS, net passes the cocoa through (inventory credited at cost, the value-minus-cost difference to `4030 Cocoa Pass-through`) with only margin, haulage and that difference as income. The app never makes the principal-versus-agent call; it posts what the setting says. No VAT is applied to contract deliveries (raw agricultural produce). Pure logic in `src/lib/contracts.ts`, server functions in `src/app/actions/contracts.ts`, the screen in `contracts-panel.tsx`.
- **Opening balances and go-live** (per entity, **Go-live** screen) — moving an entity onto the app at a **cut-over date** you choose (`Entity.cutOverDate`; fixed once anything is posted). The app builds an **Excel template** for that entity (`exceljs`), pre-filled with its chart, commodity grades, locations, agents and contacts, with a Read-me sheet and one sheet per section: trial balance, customer invoices, supplier bills, stock, agent floats, farmer advances, contracts. Amounts are ordinary decimals in the row's currency and weights are kilograms; the parser converts to minor units and grams. An upload becomes one **draft batch per sheet** (`OpeningBatch`, rows kept as JSON); a sheet with any error is not saved at all and the errors come back **by row number**. **The invariant**: the trial balance must balance in functional currency or it will not post, and it posts as one `OPENING` journal with every **control account redirected to `3090 Opening Balance Suspense`**; each detail sheet then posts to its control account **against suspense**. Suspense is therefore exactly the difference between the detail and the trial balance — never absorbed, always visible. Imports create ordinary records: open invoices and bills become posted documents (so Payments settles them later), stock becomes balances and lots, floats become open `FloatAdvance` rows with no bank movement, farmer advances become `FarmerAdvance` (`1070`), contracts become open contracts with a `BEFORE_CUTOVER` delivery that counts toward quantity and carries no revenue or cost. Foreign balances keep their currency and the cut-over rate on the journal line, so the period-end revaluation sees them. The **go-live checklist** ticks each item as it reconciles — cut-over date, trial balance, each control (trial balance vs detail vs difference), every foreign row rated, contracts, and suspense zero — and **`goLive` is refused while any is outstanding**, naming what. After go-live, every opening import is refused; corrections are ordinary journals. Pure logic in `src/lib/opening.ts`, the workbook in `src/lib/data/opening-xlsx.ts`, server functions in `src/app/actions/opening.ts`, the screen in `opening-panel.tsx`.
- **Mobile money and farmer payments** (per entity, **Payments** screen) — a **mobile money wallet is a bank account** (`BankAccount.kind = MOBILE_MONEY` with a provider and a number), in its own currency, with its own GL account under cash, reconciled the same way as any other. **Statement import**: a named **column mapping per provider** (`StatementMapping`; MTN MoMo, Telecel Cash and AT Money are supplied ready to use) says which column holds the date, description, reference, amount — or money in and money out — the fee, the levy and the balance, plus the words that mark a row as a charge in its own right. On import the **fee and levy come off each line**, so a GH₵1,000 payment that cost GH₵15 in charges still shows as GH₵1,000 and matches the payment it settled; **every fee, levy and charge-only line posts in one journal to `6050 Mobile Money Charges & Levies`** against the wallet, never left as an unmatched difference. Rows that cannot be read are reported **by row number** and the rest still import. **Payment batches**: many farmers in one `FarmerPaymentBatch` (`MP-0001`…), exported as the flat CSV a bulk disbursement takes (wallet, plain amount, per-row reference, name — refused while any payee has no wallet number), then **matched and settled in one step** when the statement line for it arrives, by reference or by the same total within three days. Two batches that would both fit are left unmatched rather than guessed. **Where the fee is posted, once**: with the import; a batch settled from a statement line posts the payment alone, and only a batch marked paid by hand books its own fee. **Farmer advances**: `recordFarmerAdvance` posts Dr `1070` / Cr the wallet; when that farmer next delivers, `postAgentPurchases` recovers it **automatically** — oldest advance first, never more than the delivery is worth — writing an `AdvanceRecovery` per advance and fixing `recoveredMinor` and `payableMinor` on the purchase, so the purchase shows the farmer's remaining balance. A purchase the agent settled credits the **float with the net only**; one left for the office credits `2060 Farmer Payables`. **Payment evidence**: a cash payment in the field will not sync without the farmer's **signature or thumbprint captured on the agent's device** (a canvas mark stored with the purchase), and a mobile money payment will not sync without its transfer reference. **Farmer history**: every farmer with what they owe on advances and what is owed to them, and one report of their deliveries, payments, advances and recoveries. Pure logic in `src/lib/momo.ts`, readers in `src/lib/data/momo.ts`, server functions in `src/app/actions/momo.ts`, the screen in `payments-panel.tsx`, capture in `src/app/field/field-form.tsx`.
- **Grants** (Sprouted Roots only, **Grants** screen) — a management layer on top of the existing fund tracking: a grant names the restricted fund its money belongs to, and everything coded to the grant is coded to that fund too. The record holds donor, award **in the donor's currency** with the rate it was agreed at, start and end, restricted or unrestricted, reporting frequency, and any number of **conditions** with due dates. **Budget lines** are in the donor's currency; **every expense charged to a grant also names a budget line** — a bill line with one and not the other is refused, as is a budget line belonging to another grant or a document dated outside the grant period. The coding travels from the document line into the **journal line** (`JournalLine.grantId`/`budgetLineId`/`fundId`), and the aggregation key for a document's journal is account **plus** coding, so one account charged to two grants makes two journal lines. Budget against actual therefore reads straight off the ledger, per budget line and per period, **in both currencies** — budgets as the donor agreed them, actuals converted at the grant's rate — with lines flagged **overspent** (past budget), **significantly underspent** (below a configurable share, default 75%, of what the elapsed time suggests, and never in the first quarter of the grant) or **not budgeted**. **Income recognition is a per-grant choice made by a person and stored on the grant**; it cannot be switched once money has come in under it. On receipt: income the day it lands. Deferred: `2070 Deferred Grant Income` until earned, then released **as eligible spending happens** (the amount is computed — spending not yet released, capped at what has actually been received) or **as a condition is met** (stated and capped the same way). A grant still holding deferred income cannot be closed. **Donor reports follow the donor's own periods**, anchored on a reporting start date that has nothing to do with our year end, each with the date its report is due; they export to **Excel** (`exceljs`) as summary, budget against actual, reporting periods, conditions, in-kind and staff time. **In-kind contributions** are grossed up — `6055` expenditure against `4035` income — so the donor sees what was given and the surplus does not move. **Staff time** is hours × rate; charging it to a grant debits and credits the *same* salary account, only the debit carrying the grant code, so the entity's total cost is unchanged and only the analysis moves — or it can be recorded for the report without touching the accounts. Pure logic in `src/lib/grants.ts`, readers in `src/lib/data/grants.ts`, the workbook in `src/lib/data/grant-xlsx.ts`, server functions in `src/app/actions/grants.ts`, the screen in `grants-panel.tsx`.
- **Settings** — **ledger export** per entity: a checksummed JSON file of the entity's accounts, contacts, funds, projects and audit trail (`src/lib/export.ts`, `BackupRun` table). Runs nightly from `src/instrumentation.ts` at server boot, or on demand. A failed export returns HTTP 500, is written to the audit trail, and is shown in red; the green panel reads the last *successful* run, never the last run. Downloads are verified against the stored checksum before being served (409 on mismatch). The most recent 14 files per entity are kept; `BackupRun` rows are never deleted. `EXPORT_DIR` sets the location. Database-level backups are the database platform's job (Supabase daily backups / PITR). Append-only audit log (`AuditEvent` table, SHA-256 hash chain per entity with a per-entity `sequence` allocated under an advisory lock, no update/delete anywhere; `GET /api/audit` requires an `entityId` and returns 400 without one) recording every posting, edit, void, bank match, period filing and export with user and timestamp; chain verification badge.

## Key conventions (enforced)

- Money is integer **pesewas** everywhere; display divides by 100. Never floats for storage. In Postgres the money columns are `BigInt` (Postgres's `Int` is 32-bit and would cap a line at GHS 21.4M). **Every Prisma read goes through `src/lib/data/`**, which converts to JS `number` with `toMinor()`; generated Prisma types carrying `bigint` never leave that folder. A `bigint` that leaks fails as "Cannot mix BigInt and other types" far from its source, or as an unserialisable export — `assertNoBigInt` in `money.ts` names the offending path instead.
- The Ghana levy rule lives in `src/lib/ghana-tax.ts` and nowhere else. VAT, NHIL and GETFund are separately assessed and separately recoverable, so each is rounded independently rather than carved out of one 20% figure. The document form, the journal builder, the tax report and the tests all call it — there were once two implementations that disagreed, and invoices did not tie to the VAT return.
- Every record carries `entityId`; every query is entity-scoped. Adding a fourth entity must need no schema change. `Entity.id` **is** the slug the UI uses (`sprouted-roots`); `code` is the statutory short code (`SG001`). There is one identifier and no alias table.
- Contacts are shared across the group (the same supplier serves all three entities); scoping happens on `ContactEntityBalance` and, once persisted, `Document`.
- Double-entry only; nothing is hard-deleted — corrections are reversing entries.
- The UI says "money in / money out", never "debit / credit".
- `AuditEvent.metadataJson` is text, deliberately not `jsonb`: Postgres reorders jsonb keys and the stored bytes must be exactly the bytes that were hashed.
- Demo data lives in `src/lib/seed-data.ts` and nowhere else; the seed writes it and the page reads it back from the database. The demo ledger for reports is still `src/lib/report-data.ts`.
- `src/app/page.tsx` is an async Server Component (`force-dynamic`) that loads everything the shell needs through `loadInitialData()` and passes one `initialData` prop. Server functions end with `refresh()` from `next/cache`; the shell mirrors the refreshed prop into its editing state in one effect, adopting the server copy only when a document's status has moved on, so an in-flight edit is never clobbered by its own autosave echo.
- **Every Server Function and Route Handler authorizes first, through `src/lib/dal.ts`.** `requireEntityAccess(entityId, permission)` builds the principal from the library's session (never from anything the client sent), loads their `UserEntityAccess` rows, and asks the pure matrix in `src/lib/authz.ts`. Nothing is read or written before that check — `tests/entity-isolation.test.ts` proves it for every exported function and handler with a database fake that records every call. The UI hiding a button is a courtesy; the DAL is the check. `src/proxy.ts` only redirects visitors with no session cookie to sign-in.
- Entity scoping is in the queries, not applied afterwards: `loadInitialData(principal)` passes `entityId IN (...)` to every table. An entity a user cannot see is refused with the same message as one that does not exist.
- Rates never touch floats: `parseRate`/`convertMinor` in `src/lib/fx.ts` use BigInt scaled by 1e10 with one half-away-from-zero rounding. A rate is a decimal *string* everywhere outside Prisma (`rateText` converts the Decimal at the boundary).
- The identity on journals (`postedById`), documents (`createdById`, `lastEditedById`), filings (`filedById`) and audit events (`userId`, part of the hash) is the session's user id. Audit events written by scheduled jobs carry `userId = NULL` and `userName = 'system'`.
- Better Auth model names are given as Prisma *client properties* (`authSession` → `prisma.authSession` → table `AuthSession`); the adapter's schema check compares them verbatim. The tables are prefixed because `Account` is the chart of accounts.
- `Document.number` is **NULL while a draft** and allocated on posting. It is part of a unique index with `entityId`; an empty string there would stop an entity holding a second draft (it did, once).
- `seedChartForEntity` is one read plus batched inserts, not one upsert per account: it runs inside `createEntity`'s transaction, and ~50 sequential round trips to a remote database exceed Prisma's 5-second interactive-transaction default. The seed script raises its own transaction timeout for the same reason.
- The export scheduler's "already started" flag lives on `globalThis`, like the Prisma client: `instrumentation.ts` and the API routes are bundled separately and each get their own module instance. An empty `EXPORT_DIR=` means the default directory, not `mkdir('')`.
- Files that plain Node loads (the seed script and everything on its import path — `src/lib/data/chart.ts`, `enums.ts`, `seed-data.ts`, `account-templates.ts`) use `.ts` extensions on relative imports and never import `@/` at runtime. Node 24's native type stripping resolves relative imports strictly. `allowImportingTsExtensions` is on in `tsconfig.json` for this.

## Known gaps / next steps

1. **Reports, tax, intercompany, bank and the dashboard still read demo arrays** — `ledgerLines` and `reportAccounts` in `report-data.ts`, and `taxTransactions`, `intercompanyTransactions`, `bankDocuments`, `initialBankLines`, `metricsByEntity`, `summaryRows` in the shell. Documents you post are in the ledger but do not yet appear in any report. Next-pass path: a query over `JournalLine` ⋈ `Account`/`Contact`/`Project` producing the existing `LedgerLine` DTO shape, so the report memos in the shell need no change; then `report-data.ts` is deleted.
2. **Not persisted yet:** bank lines, matches and codings; intercompany transactions (the matrix's multi-currency handling runs over the demo transactions, each side taken in its entity's functional currency). Reports translate the demo ledger; the translation option and label are wired for when reports read the real ledger. These still live in component state and audit through `POST /api/audit` from the client.
3. **Auth is built** (see above). Remaining in that area: `period:unlock` is defined in the matrix (Owner only) but no unlock feature exists yet; there is no self-service "change password" or "reset my TOTP" — an Owner re-sends an invite link for the former, and a user who loses both device and backup codes needs an Owner to clear `TwoFactor` (not yet a button); `USER` audit events are recorded per granted entity, so a change to an Owner is written to every entity's trail.
4. **Bank reconciliation persistence** — matches, codings and imported lines should write journals and update document payment status. CSV import currently stores parsed **cedis** while everything else is pesewas (`parseAmount`).
5. **Intercompany** posts hardcoded `1010/4001` and `5001/2001`, ignores VAT, and ignores the chart's dedicated intercompany accounts (`1025–1027`, `2015–2017`).
6. **Navigation structure** — the single-shell `activeNav` pattern could be split into real routes once persistence exists. Inventory is its own component (`inventory-panel.tsx`); the rest of the shell is still one file.
10. **Sales go through contracts, not invoices**: a contract delivery relieves stock and posts revenue and COGS; the invoice editor still does not (an invoice is a document, not a stock movement). If cash sales without a contract are needed, the next step is an invoice line naming a grade and location, relieved the same way. A delivery cannot be reversed yet (no "return from buyer"); the receivable a delivery creates is settled through Payments only once an invoice exists for it — recording cash against a contract delivery directly is the other gap. Also not yet built: editing or reversing a posted field purchase, and the offline form has been exercised in a desktop browser but not yet on a phone in the field.
7. **GRA E-VAT** — placeholder fields only; add the integration later without redesigning. The VAT return screen (Tax) is hidden while an entity is unregistered and still reads demo `taxTransactions` when shown; once it reads the ledger it should take `Document.vatApplied` and `importVatMinor` into account. Switching registration off is allowed but there is no deregistration workflow (final return, stock adjustment) — posted documents simply keep the VAT they were posted with.
8. **Deployment** — `render.yaml` targets Render's Node runtime with `prisma migrate deploy` at the front of `startCommand` (the free tier has no `preDeployCommand`; move it there on a paid instance). Not yet deployed. On the free plan the disk is ephemeral, so `EXPORT_DIR` needs a Render Disk for exports to persist across deploys.
9. **Prisma 7** changes the generator and adds a config file. Do not bump the major version casually.
13. **Grants**: only **bills** can be coded to a grant — an invoice cannot, so grant income billed to a donor is recorded as a receipt rather than raised as an invoice. Budget lines have no per-period phasing, so "significantly underspent" prorates the whole budget by elapsed time rather than following an agreed spending profile. The donor's rate is fixed at award: a grant is not revalued, and a large move in the cedi will show a budget the donor no longer recognises. A grant receipt cannot be reversed from the screen, and neither can an in-kind or staff-time posting; corrections are ordinary journals. Staff time is not checked against payroll actually posted, so someone can allocate more hours than were paid for.
12. **Mobile money**: the **Bank** screen is still the demo reconciliation — real statement import and matching live on **Payments**, and the two are not yet one screen. A statement import cannot be undone (its charges journal would need reversing by hand), there is no duplicate-file guard beyond the operator noticing, and an unmatched line can only be noted, not posted to an account. A batch cannot be part-paid: it settles in full or not at all. The signature pad has been exercised with a mouse, not a finger on a phone.
11. **Opening balances** are one-way: a posted batch cannot be un-posted, only corrected by journal, and changing the cut-over date once anything is posted is refused. Removing an entity's opening balances wholesale (to start again) is a database job, not a screen. The template's Read-me explains the sheets, but there is no per-row help in the app beyond the error list.

## How to run

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass  # needed on this Windows machine
copy .env.example .env      # then fill in DATABASE_URL and DIRECT_URL
npm install                 # also runs `prisma generate`
npx prisma migrate deploy   # applies prisma/migrations to the database
npm run prisma:seed         # entities, charts, contacts, funds, projects — idempotent
npm run auth:create-owner -- --email you@example.com --name "Your Name"   # first Owner, no password yet
npm run dev                 # http://localhost:3000 → /forgot-password to set the Owner's password
                            # (without RESEND_API_KEY the link is printed to this console)
npm test
npm run lint
npm run build
```

`npx prisma migrate dev --name <change>` creates a new migration after a schema edit and re-runs the seed.

## Exports

Export files land in `EXPORT_DIR`, defaulting to `exports/` next to the app (git-ignored — an export contains the whole ledger and must never be committed). The Settings page shows the last successful export for the selected entity, flags a failed one in red, and offers verified downloads.

The scheduler is an in-process timer that runs one export per entity nightly. It suits a long-running server; on a host that sleeps idle services it runs when the service next wakes. It is a convenience copy — the database platform's own backups are the real safety net.
